# Workforce attendance correction requests

## Goal

Add an auditable attendance-correction workflow on top of the existing VPS-owned attendance module without changing payroll formulas.

1. employee/part-time may request a correction only for their own attendance record;
2. manager/admin with attendance edit authority may approve or reject pending requests;
3. approval applies only the explicitly requested attendance fields through a server-side mutation;
4. any applied correction invalidates an existing attendance approval so the corrected row must be reviewed again before payroll lock;
5. locked payroll periods reject new correction application until the period is reopened through the existing audited reopen workflow;
6. every lifecycle transition is persisted on the VPS and written to the database audit log.

## Storage boundary

The workflow remains inside the existing PostgreSQL `business_state.modules.attendance` JSONB document:

- `attendance.attendance`: canonical attendance rows;
- `attendance.correctionRequests`: server-owned correction requests;
- `attendance.payroll.periods`: existing payroll lock/reopen state.

No SQL migration is required for this phase.

Generic attendance writes must preserve `correctionRequests`. Clients cannot forge request status, decision metadata, applied fields, or actor metadata through the generic business-state endpoint.

## Authority

### Employee / part-time

- May submit a correction only for the authenticated account's VPS-resolved staff identity.
- May target only an attendance record visible in own self-service scope.
- May view only own correction requests.
- May cancel only an own `pending` correction request.
- Cannot approve or reject correction requests.
- Cannot directly mutate a completed attendance row through this workflow.

### Admin / manager

- Must have `attendance.edit` permission and an allowed site.
- May view branch correction requests.
- May approve or reject a pending request.
- Reject requires a non-empty decision note of at least 3 characters.
- Supervisor remains non-management for correction decisions even if stale legacy permission bits exist.

## Request model

A correction request is server-owned and contains:

- `id`
- `attendanceId`
- `staffId`
- `staffName`
- `date`
- `sourceSnapshot`
- `changes`
- `reason`
- `status`: `pending`, `approved`, `rejected`, or `cancelled`
- `createdAt`, `createdByUserId`, `createdByName`
- decision/cancellation actor and timestamp fields generated by the VPS

Supported `changes` are limited to attendance facts already supported by the canonical attendance model:

- `clockIn`
- `clockOut`
- `breakMinutes`
- `scheduledStart`
- `note`

Hourly rate is deliberately excluded from employee correction requests. Pay-rate changes remain a management/configuration concern and must not be inferred from a correction request.

At least one supported field must change. Unknown fields are rejected.

## Source consistency

A request captures a source snapshot of the targeted attendance row. Approval must verify that the current row still matches the captured source identity and relevant attendance values.

If the row changed after submission, approval fails closed with `WORKFORCE_ATTENDANCE_CORRECTION_STALE`; the request remains pending so a user or manager can cancel/reject and submit a fresh request.

## Payroll lock interaction

- If the attendance row belongs to a payroll period whose status is `locked`, correction approval returns `WORKFORCE_PAYROLL_PERIOD_LOCKED`.
- Managers must use the existing audited payroll reopen workflow before applying a correction.
- Applying a correction clears existing attendance approval metadata (`approvalStatus`, approval actor/time fields), because payroll must use a newly reviewed corrected row.
- Existing payroll math is unchanged.

## Validation

- ISO timestamps must parse successfully when provided for `clockIn` or `clockOut`.
- If both resulting timestamps exist, `clockOut` must not precede `clockIn`.
- `breakMinutes` must be a finite integer >= 0.
- `scheduledStart` must be a valid timestamp when provided.
- `reason` is required and trimmed.
- Requests that produce no canonical value change are rejected.

## UI

The existing Attendance tab in the workforce module gains a correction-request workspace; no new top-level route is introduced.

Employee/part-time:

- correction action on own attendance rows;
- current values shown read-only next to requested values;
- required reason;
- recent own request history;
- cancel control only for own pending requests.

Admin/manager:

- pending correction queue with source values and requested delta;
- approve/reject controls;
- reject requires decision note;
- status/history visible for reconciliation.

Traditional Chinese and Vietnamese labels are required. Desktop and mobile use the same canonical behavior and permission rules.

## Audit requirements

Database `audit_logs` records:

- correction request creation;
- pending request cancellation;
- manager approval and exact applied field delta;
- manager rejection with decision note;
- invalidated prior attendance approval metadata when approval applies a correction.

## Regression requirements

Backend/API coverage must prove:

- self-service identity and `attendanceId` ownership cannot be spoofed;
- employee/part-time sees only own correction requests;
- own pending cancellation only;
- supervisor cannot decide requests;
- manager/admin with attendance edit can approve/reject;
- rejection reason is required;
- unsupported fields and invalid time ranges are rejected;
- stale source row blocks approval;
- locked payroll period blocks approval;
- approved correction clears prior attendance approval metadata;
- generic business-state writes preserve server-owned correction workflow data;
- payroll lock still requires all corrected completed rows to be re-approved.

Browser coverage must prove employee submission/history and manager decision controls on mobile Chromium while existing workforce, full-device, concurrency, persistence and production smoke gates remain required.
