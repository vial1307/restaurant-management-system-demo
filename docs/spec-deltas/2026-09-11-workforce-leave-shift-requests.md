# Workforce leave and shift-change requests

## Goal

Add an auditable schedule-request workflow on top of the existing workforce schedule without changing payroll math:

1. employee/part-time may submit an own leave request or shift-change request;
2. employee/part-time may cancel only an own pending request;
3. admin/manager with schedule edit permission may approve or reject pending requests;
4. approved requests create server-owned schedule exceptions for the requested service date;
5. effective schedule resolution applies approved exceptions before the base date-specific or recurring schedule;
6. every request transition is persisted on the VPS and written to the database audit log.

## Storage boundary

The workflow remains inside the existing `schedule` business module in PostgreSQL JSONB:

- `schedule.schedules`: existing base schedules;
- `schedule.requests`: server-owned leave/change requests;
- `schedule.exceptions`: server-owned approved schedule exceptions.

No SQL migration is required.

Generic schedule writes may edit `schedules` but must preserve the VPS-owned `requests` and `exceptions` collections. A generic business-state write cannot forge, approve, reject, cancel, overwrite, or delete request/exception workflow records.

## Authority

### Employee / part-time

- May create a request only for the authenticated account's VPS-resolved staff identity.
- Any submitted `staffId`, `staffName`, creator identity, status, decision fields, or exception fields from the client are ignored and generated server-side.
- May view only own schedules, requests and exceptions.
- May cancel only own `pending` request.
- Cannot approve or reject requests.
- Existing clock-in/out self-service rules remain unchanged.

### Admin / manager

- Must have `schedule.edit` permission.
- May view all requests for an allowed site.
- May approve or reject a pending request.
- Reject requires a non-empty decision note of at least 3 characters.

### Supervisor

Supervisor remains non-management for workforce scheduling. Legacy/stale generic permission bits do not grant request approval/rejection authority.

## Request model

A request contains server-owned identity and lifecycle metadata:

- `id`
- `type`: `leave` or `change`
- `staffId`
- `staffName`
- `date`: `YYYY-MM-DD`
- `sourceScheduleId`
- `sourceSnapshot` when a matching source schedule exists
- `requestedStart` / `requestedEnd` for `change`
- `reason`
- `status`: `pending`, `approved`, `rejected`, or `cancelled`
- `createdAt`, `createdByUserId`, `createdByName`
- decision/cancellation actor and timestamp fields generated by the VPS

A shift-change request requires valid `HH:MM` start/end values and a uniquely resolved source schedule for the requested staff/date. A leave request may be submitted for a date even when no source schedule exists, but approval still produces an explicit leave exception for that date.

## Source-schedule consistency

When a request captures a `sourceSnapshot`, approval must verify that the current matching base schedule still has the same scheduling identity and time/department values. If it changed while the request was pending, approval fails with `WORKFORCE_REQUEST_SCHEDULE_CHANGED`; the old request is not silently applied to a different schedule.

## Exception model

Approved requests create one server-owned exception per request:

- `id`
- `requestId`
- `staffId`
- `date`
- `kind`: `leave` or `override`
- `sourceScheduleId`
- `start`, `end`, `department` for an override
- approval actor/time metadata

A second active exception for the same staff/date is rejected instead of being stacked ambiguously.

## Effective schedule resolution

For a staff member and service date:

1. inspect approved schedule exceptions for that staff/date;
2. exactly one `leave` exception means no scheduled start for that date;
3. exactly one `override` exception supplies the effective start/end;
4. multiple exceptions fail closed;
5. otherwise use the existing unique date-specific schedule;
6. otherwise use the existing unique recurring month + weekday schedule;
7. ambiguous base schedules fail closed as before.

The attendance `scheduledStart` canonicalization must use this effective resolver so future clock-ins respect approved leave/change requests.

## Payroll boundary

- Leave approval does not imply paid leave, unpaid leave, wage deduction, bonus, overtime, holiday multiplier, insurance, tax, or any other payroll rule.
- Shift-change approval changes only the effective planned schedule.
- Canonical attendance/payroll calculations remain unchanged.

## UI

The existing `#schedule` workforce panel gains a request workspace without a new top-level route.

Employee/part-time:

- own leave/change form;
- date defaults to the selected service date;
- change requests show requested start/end fields;
- reason required;
- recent own request history;
- cancel control only for pending own requests.

Admin/manager:

- pending request queue with request details;
- approve and reject actions;
- reject requires decision note;
- request history/status visible for reconciliation.

Bilingual status labels are required for Vietnamese and Traditional Chinese.

## Audit requirements

Database `audit_logs` records:

- request creation;
- pending request cancellation;
- manager approval;
- manager rejection with decision note;
- generated exception details on approval.

## Regression requirements

Backend/API coverage must prove:

- self-service identity cannot be spoofed;
- self-service sees only own requests/exceptions;
- employee/part-time cancellation is own + pending only;
- supervisor cannot approve/reject;
- manager/admin with schedule edit can approve/reject;
- rejection reason is required;
- approval creates the correct exception;
- duplicate staff/date exception is rejected;
- stale source schedule blocks approval;
- generic schedule writes cannot mutate server-owned workflow data;
- approved exception changes canonical scheduled-start resolution.

Browser coverage must prove employee request controls and manager decision controls are role-correct on mobile, while existing full-device, persistence, concurrency and permission regressions remain green.
